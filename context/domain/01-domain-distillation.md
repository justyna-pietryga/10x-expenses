### Product Purpose

The product is a personal finance web app for monthly budget review. The PRD states that users need to "review bank account data at the end of every month, calculate all expenses, and divide them into personally defined budget categories" (`context/foundation/prd.md:20`). The key gap is that bank categories do not match user-defined budget categories, do not consolidate across banks, and do not calculate spending as a percentage of income with carry-over behavior (`context/foundation/prd.md:22`). The primary success criterion is that a logged-in user can import bank statements, define income/categories/limits, review and adjust transaction categories with reusable rules, and see a monthly budget summary (`context/foundation/prd.md:32`).

### #1 Refactoring Target

Refactor the `Statement Import Batch + Transaction Review` aggregate first. It owns the highest-value transition from untrusted imported statement data to trusted monthly summary input, and it currently spreads lifecycle rules across DB constraints, parser checks, API helpers, and React dirty-state controls. A better domain boundary should make the batch states explicit: `previewed`, `persisted`, `pending_review`, `completed_once`, `replaced`, with operations such as `replaceWithConfirmedImport`, `applyReviewUpdates`, `excludeTransaction`, `createRuleFromReviewedRow`, and `completeReview`. The immediate risk to reduce is completion semantics: the backend should understand what "complete" means, or the model should explicitly rename it to "user marked complete" and keep summary trust buckets resilient.
